# Архитектура прошивки

Этот документ объясняет, как устроен код проекта и почему именно так.
Прочитайте перед тем, как начать писать свой модуль — это сэкономит
время всем.

## Цель архитектуры

Нас много, опыта в C++ и embedded пока немного, а работать нужно
параллельно, не мешая друг другу. Поэтому у архитектуры три простых
правила, а не "полноценные" паттерны/ООП/DI — этого осознанно нет,
и вот почему:

- Мы не используем **классы и наследование** для модулей — только
  `namespace` со свободными функциями (`Init()`/`Update()`). Это даёт
  почти всё, что даёт "модуль" в ООП (свой файл, свои данные, свой
  публичный API из `.h`), но без виртуальных функций, конструкторов,
  указателей на объекты и прочего, что пока незнакомо.
- Мы не используем **Dependency Injection** — вместо "передайте мне
  ссылку на объект Dispenser, чтобы я мог его вызвать" у нас общая
  событийная шина (`EventBus`) и общее состояние (`AppState`). Модули
  не держат ссылок друг на друга вообще.
- Мы **не делаем это "неправильным" или временным** — это осознанный,
  вполне взрослый архитектурный стиль (близкий к тому, что в больших
  системах называют event-driven / pub-sub архитектурой, а сама идея
  "модуль публикует то, что произошло, не зная, кто слушает" — это
  упрощённая версия паттерна Observer). Когда вы позже пройдёте ООП,
  SOLID и DI в учёбе, вам будет проще понять их ценность, увидев
  сначала, как без них можно жить в небольшом проекте.

## Три правила

### 1. Модуль = папка в `src/modules/<name>/` с `Init()`/`Update()`

Каждый модуль — это `<name>.h` + `<name>.cpp` внутри `namespace <Name>`.
Два обязательных публичных метода:

```cpp
namespace Dispenser
{
    void Init();    // вызывается один раз из setup(), через App::Init()
    void Update();  // вызывается на каждой итерации loop(), через App::Update()
}
```

Модуль не подключает (`#include`) заголовки других модулей из
`src/modules/`. Если модулю А нужно что-то от модуля Б — это делается
через EventBus или AppState (правила 2 и 3), а не напрямую. Так любой
модуль можно писать, тестировать на столе и переписывать, не боясь
сломать чужой код, и не читая его весь целиком.

Чтобы подключить новый модуль к прошивке, добавьте его `Init()`/`Update()`
в `src/app/app.cpp` — это единственное место, которое знает про все
модули сразу.

### 2. Общие данные — в `AppState` (`src/core/app_state.h`)

`AppState` — одна структура на весь проект, "источник правды" для
данных, которые нужны нескольким модулям (подключён ли Wi-Fi, занят ли
диспенсер и т.п.). Читать поля может любой модуль, писать — только тот,
кто за поле отвечает (это указано в комментарии рядом с полем в
`app_state.h`).

Это не "база данных" и не замена событиям — сюда кладём именно
*текущее состояние*, а не *события*. Разницу поясняет правило 3.

### 3. Уведомления между модулями — через `EventBus` (`src/core/event_bus.h`)

Если модулю нужно не просто прочитать состояние, а **сообщить о
событии** ("Wi-Fi подключился", "сработал датчик препятствия") —
используется `EventBus::Publish()`/`EventBus::Subscribe()`.

```
Connectivity ──Publish(NetworkConnected)──▶  EventBus  ──▶  Display (подписан)
```

Ключевая мысль: **Connectivity ничего не знает про существование
Display**, и наоборот. Можно добавить второй/третий модуль, который
тоже реагирует на подключение к сети — и для этого не придётся менять
ни одной строчки в уже существующих модулях. Это и есть "общий API
для взаимодействия", про который договаривались: не общий класс с
кучей методов, а общий список событий. Рабочий пример подписки —
`OnNetworkConnected` в
[`src/modules/display/display.cpp`](../src/modules/display/display.cpp).

**Как добавить новое взаимодействие:**

1. Откройте `src/core/event_bus.h`, добавьте новый `EventType` в
   перечисление (обязательно перед `EventTypeCount`), опишите его
   коротким комментарием — что значит, кто публикует, кто может
   слушать.
2. В модуле-источнике: `EventBus::Publish({EventBus::EventType::Ваш, значение});`
3. В модуле-получателе, в `Init()`:
   `EventBus::Subscribe(EventBus::EventType::Ваш, ВашОбработчик);`

Обработчики событий (как и `Update()`) должны отрабатывать быстро и не
блокировать выполнение — см. следующий раздел.

## Блокирующие операции: `delay()` и почему его нельзя

`loop()` в Arduino/ESP32 выполняется в бесконечном цикле, и это же
касается `App::Update()` и `Update()`/обработчиков событий каждого
модуля. Если где-то внутри вызвать `delay(1000)` — **на всю секунду
останавливается вообще всё**: не крутится сервопривод, не
перерисовывается экран, не опрашивается датчик препятствия, не
отвечает телеграм-бот. На одном микроконтроллере, который отвечает
сразу за экран, механику и сеть (наш случай), это особенно критично —
одна "мелкая" задержка в одном модуле тормозит все остальные.

**Считайте блокирующими** и избегайте в `Update()`/обработчиках:
- `delay()`, `delayMicroseconds()`;
- `pulseIn()` без таймаута;
- ожидающие циклы вида `while (!condition) {}` без выхода по времени;
- сетевые вызовы, которые сами внутри ждут ответ (например
  `WiFi.waitForConnectResult()`, синхронные HTTP-запросы с большим
  таймаутом) — используйте неблокирующие/асинхронные варианты
  библиотеки или опрашивайте состояние по кусочкам, как в примере ниже.

**Альтернатива — неблокирующий таймер на `millis()`.** Идея: вместо
"подождать N мс" запоминаем время старта и на каждом тике `Update()`
только проверяем, прошло ли уже N мс, ничего не блокируя между
проверками:

```cpp
unsigned long actionStartedAtMs = 0;
bool actionInProgress = false;

void StartAction()
{
    actionInProgress = true;
    actionStartedAtMs = millis();
    // включить то, что нужно (мотор, звук и т.п.)
}

void Update()
{
    if (actionInProgress && millis() - actionStartedAtMs >= 800)
    {
        actionInProgress = false;
        // выключить/завершить действие
    }
    // ...остальной Update() продолжает выполняться каждый тик, ничего не ждёт
}
```

Если состояний/переходов больше одного (не просто "делаем" →
"закончили", а целая последовательность шагов) — тот же приём
оформляется как конечный автомат (`enum class` с состояниями +
`switch` в `Update()`). Более простой вариант того же приёма —
периодический опрос раз в N мс без состояний — уже реализован и
рабочий в
[`src/modules/sensors/sensors.cpp`](../src/modules/sensors/sensors.cpp)
и [`src/modules/power/power.cpp`](../src/modules/power/power.cpp).

Если задача принципиально не влезает в "неблокирующий тик" (например,
действительно долгая и сложная последовательность) — не деляйте это
молча, а обсудите с лидом/мейнтейнерами: на ESP32 есть более
продвинутые инструменты (например, отдельная FreeRTOS-задача через
`xTaskCreate`), но это уже следующий уровень сложности, вводить его
стоит осознанно и только когда правда нужно. Я лично не советую копать
в этом направлении без крайней необходимости.

## Как добавить новый модуль — по шагам

1. Создайте папку `src/modules/<name>/` с `<name>.h` и `<name>.cpp`.
2. В `.h` объявите `namespace <Name> { void Init(); void Update(); }`
   и коротким комментарием опишите, за что модуль отвечает, какие
   события публикует/слушает (по аналогии с уже существующими
   модулями).
3. В `.cpp` реализуйте `Init()`/`Update()`. Пины берите из
   `src/core/pins.h` (не хардкодьте номера прямо в коде модуля).
   Секреты (токены/пароли) — из `src/core/config.h`
   (`config_local.h`, не в git).
4. Подключите модуль в `src/app/app.cpp`: добавьте `#include`,
   вызов `<Name>::Init()` в `App::Init()` и `<Name>::Update()` в
   `App::Update()`.
5. Если библиотека новая — добавьте её в `lib_deps` в
   `platformio.ini` **и** поставьте через Library Manager в
   Arduino IDE (см. корневой README, раздел про библиотеки) — иначе
   проект соберётся только в одном из двух инструментов.
6. Скопируйте `docs/module-template.md` в `docs/modules/<name>.md` и
   заполните.
7. Заводите ветку и PR как описано в корневом README.

## Структура репозитория

```
feeder-for-students/
├── feeder-for-students.ino     # точка входа: setup()/loop() → App
├── platformio.ini              # конфигурация PlatformIO
├── justfile                    # команды build/upload/monitor и т.п.
├── docs/                       # документация проекта (этот файл и др.)
│   └── modules/                # документация по каждому модулю
└── src/
    ├── core/                   # общие для всех модулей вещи
    │   ├── pins.h               # распиновка платы (единственный источник)
    │   ├── config.h              # общие настройки + подключение config_local.h
    │   ├── app_state.h            # общее состояние (AppState)
    │   └── event_bus.h/.cpp        # событийная шина между модулями
    ├── app/
    │   └── app.h/.cpp            # сборка модулей: кто и в каком порядке
    └── modules/
        ├── display/               # экран, UI, QR-код
        ├── dispenser/             # механика выдачи (моторы/серво)
        ├── sensors/                # датчики препятствия и т.п.
        ├── connectivity/            # подключение к Wi-Fi
        ├── telegram_bot/             # Telegram Bot API
        └── power/                     # мониторинг питания
```
